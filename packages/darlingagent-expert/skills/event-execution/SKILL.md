---
name: event-execution
description: Execute a local event-planning request with DarlingAgent MCP tools and return persisted, verified files and action evidence.
---

1. Discover darlingagent-local tools. If unavailable, explain that the local connector must be enabled; do not fake execution.
2. For new work, call event_create_structured with eventId, request, budget, assumptions. request requires title; preserve supplied attendeeCount, budgetLimit, currency, date, timezone and location. Infer a timezone only when location supports it and label any assumptions. Budget entries require item, amount (max two decimals), status estimate/confirmed and note. Estimates are not vendor quotes.
3. Create dependency-linked task_create records using distinct taskId values and existing dependencyIds. Use task_update for description, workstream, priority (0 highest) and deadline; it requires the task's current revision. Use task_transition for lifecycle changes. Never finish a real-world task merely because its plan exists.
4. Call budget_validate with a unique validationId. Resolve failed arithmetic/ceiling checks before reporting a validated budget. The structured plan should be prepared carefully before creation; do not overwrite a prior event via a new ID.
5. Call registration_draft. Save its exact fields in a task_submit_result. This is a draft only. After explicit user approval, registration_create takes the SAME event/options plus unique registrationId and confirmed:true. Call registration_get afterwards. Missing key is a configuration limit, not a form link.
6. Use tool discovery for native web search/browser tools before concluding research is unavailable. Research vendors with native WorkBuddy browsing. Store only findings backed by opened sources. proposal_save content includes objectives, agenda [{time,activity}], assignments [{task,assignee,status:proposed|accepted}], vendors [{name,source,services,contact?,publishedPrice?,checkedAt:YYYY-MM-DD,verification:source_reviewed|unverified}], pendingApprovals, unresolvedIssues, invitation? {to:[],subject,body,status:draft}. First expectedRevision is 0. Read proposal_get before subsequent updates. Use invitation.to:[] when no recipient was supplied or verified; never guess university mailing lists. Include empty arrays when nothing is verified; never invent data to fill sections.
7. Call document_generate(eventId) after content is saved. It uses the existing PDF generator, reopens/hashes the result and returns absolute PDF, JSON task tracker and invitation draft paths. Read the actual PDF/file when supported to check layout. If it fails on an unsupported glyph, transliterate only the unsupported character without changing meaning, save a new proposal revision, then retry. Never claim a file from a failed call.
8. Call event_get to verify persistent state. Return IDs, budget total/ceiling/remaining, file paths and hashes, draft/live registration status, approval requests and concrete unresolved work.
9. On a later retrieval request, event_list then event_get/proposal_get recover state without repeating creation or publication.

Tool failure recovery: stale revision => read current state; duplicate ID => inspect existing record; missing Tally key => keep draft; uncertain Tally request => inspect provider manually before any new publish; browser unavailable => no verified vendors; email unavailable => unsent invitation. No hosted backend is required.
